# Pero CLI and service lifecycle

## User experience

Installation and daily control go through one globally installed npm executable:

```sh
npm install -g @perokit/pero
mkdir ~/workspace && cd ~/workspace
pero run
pero status
pero agents ls
pero stop
```

The CLI keeps what files can't do: start, stop, inspect, check, run a Workflow by hand, back up, and restore. Agents, Workflows, and the installation defaults are notes in the workspace, as [Configuring Pero](./CONFIGURATION.md) describes, so no command creates or edits them.

The package is `@perokit/pero`, published under the `perokit` npm organization from [github.com/perokit/pero](https://github.com/perokit/pero). The unscoped `pero` package name is already taken, so Pero ships as a public scoped package while keeping the terminal command `pero`. npm [scopes](https://docs.npmjs.com/about-scopes/) allow the same package suffix in a separate namespace, and the [`bin` field](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#bin) chooses the executable name independently:

```json
{
  "name": "@perokit/pero",
  "repository": { "type": "git", "url": "git+https://github.com/perokit/pero.git" },
  "bin": { "pero": "./bin/pero.js" }
}
```

The package ships compiled JavaScript, and the [Release workflow](./DEVELOPMENT.md#releasing) publishes it; `publishConfig.access` makes the scoped package public. Users need a supported Node.js/npm installation, but do not need to clone the repository, compile TypeScript, install PostgreSQL or Redis, or start a container.

## Command contract

| Command | Expected behavior |
|---|---|
| `pero -v`, `pero --version` | Print the installed version. |
| `pero init [dir]` | Make `dir` (default: `--workspace`, then the current folder) a workspace, writing only what is missing: a `.gitignore` listing `.env`, `.pero/` with its `.gitignore` and a commented `config.yaml`, and in the settings folder (`data/Settings/` unless `config.yaml` says otherwise) `Pero.md`, `Agents/Main.md`, and an empty `Workflows/`; an `Agents/_Template.md` for new topics' Agents is yours to add (see [Configuring Pero](./CONFIGURATION.md#agent-notes)). It never overwrites a file, so it fills in a cloned workspace; it prints what it created, updated, and kept. It refuses the home folder, since every folder under it would find that workspace. Runs without the daemon. |
| `pero check` | Check what Pero reads from the workspace without opening its database: `config.yaml` (including that a `data` folder it names exists), that `.env` is owner-only and not tracked or unignored by Git, and every note in the settings folder (`Pero.md`, `Agents/`, `Workflows/`) against the [configuration reference](./CONFIGURATION.md). Errors are printed under each file, relative to the workspace, with the property at fault. Exits 1 on any error, so it can run in CI on a workspace repository; `--json` prints the result for tools. With Pero running it asks the daemon, which also checks the topic titles in Workflow `channel` and `history-channels` against the topics it has seen in the allowed chats (a title matching no topic lists the ones there are; one matching several asks for `<chat title>/<topic title>`). Without Pero, those titles are checked for syntax only, and it says so. |
| `pero run` | Ensure one background Pero process is running for the selected workspace. With no workspace found, it offers on a terminal to make one as `pero init` does, in the current folder or `~/workspace` from home, asking which folder already there is the data folder (the vault Agents keep notes in): `data/` is selected when it exists, otherwise the first choice creates `data/`, and the last, *Create a new folder…*, asks the name of a new folder to create; with no folders there it asks nothing and uses `data/`; without a terminal it prints the `pero init` to run and exits 1. On a terminal, a workspace's first start (no database yet) settles the default provider before anything is made or started: a pick among the provider CLIs installed, or the one `Pero.md` sets, written to `Pero.md` as `provider:`; it refuses to start when no provider CLI is installed, or when the owner quits while it is signed out. On first use, create local directories and guide the owner through missing setup. After a first start it offers `pero service install`, and after a first start or any interactive setup it ends with `pero status`; otherwise it ends with the running process's pid and workspace. Setup output comes in blocks, one per step, separated by an empty line. Leaving setup before it finishes (Ctrl-C, Ctrl-D, a closed terminal or connection) stops the Pero this run started; one that was already running keeps running. Return only after startup and readiness succeed. Repeated calls report the existing process. |
| `pero run --foreground` | Run the same daemon attached to the terminal for debugging or an external service manager. |
| `pero service` | Say whether Pero is installed as a service of this account. |
| `pero service install` | Run Pero as a service of this account, which starts it with the machine and restarts it after a crash: on Linux a systemd user unit, `~/.config/systemd/user/pero.service`, enabled and started, with lingering turned on (`loginctl enable-linger`) so it runs while you are logged out; on macOS a launchd agent, `~/Library/LaunchAgents/com.perokit.pero.plist`. The service runs `pero run --foreground --workspace <workspace>` with this Node.js, this `pero`, and this shell's `PATH`, so it finds the provider CLIs; it does not get other environment variables, such as `PERO_TELEGRAM_BOT_TOKEN`. A Pero already running outside the service is stopped first; the command waits until the service's Pero is ready and prints its status. There is one such service per account; installing it for another workspace replaces it. |
| `pero service uninstall` | Stop the service, disable it, and remove its file. `pero run` starts Pero in the background again. |
| `pero stop` | Ask the running daemon to stop intake, cancel or finish active work within a bounded period, close the database, and exit. Report when it is already stopped. A Workflow Run stopped mid-way is recorded `interrupted` on the next start, and retried there if its Workflow allows another attempt. |
| `pero status` | Show process state, version, the workspace, health, and each component: Telegram, each Agent Runtime, `config` (`config.yaml`), and `settings` (the notes, counting those with errors). Exit with status 3 when Pero is stopped. |
| `pero logs` | Show the most recent entries of `logs/pero.log` (`-n <count>`, default 50) as readable lines in local time; `--follow` streams new entries and `--json` prints the raw JSON lines. Reads files only, so it works whether or not the daemon is running; it points to `logs/daemon.out` rather than streaming it. |
| `pero settings` | Show the settings in effect: the `Pero.md` properties, each marked `(default)` when `Pero.md` doesn't set it, `config.yaml`'s data folder, and where the Telegram bot token comes from (only as set or not set). The files are where they change: edit `Pero.md` and `config.yaml`, and set the token with `pero telegram token`. |
| `pero backup <file> [--include-data]` | Ask the running daemon to write a backup: a consistent snapshot of the database from the SQLite online backup API, archived with `config.yaml` and a manifest as an owner-only gzip tar. The database includes each Channel's message history. `--include-data` adds the data folder (its files and folders, without links). Logs, `run/`, `.env`, and other working folders are never included. The file must be outside `.pero/`, and outside the data folder with `--include-data`; an existing file is replaced. |
| `pero restore <file> [--replace-config]` | Restore a backup while Pero is stopped, never overwriting its database. Into a workspace (created when missing) whose `.pero/` has no database, such as a fresh clone: it keeps the workspace's `config.yaml`, listing the chats only the backup's allowed, unless `--replace-config`; and restores an `--include-data` backup's data folder without overwriting a file. Refuses while a daemon answers there, and warns about each folder the workspace uses that does not exist here. [Operating Pero](./OPERATIONS.md#moving-to-a-fresh-machine) describes a restore on a fresh machine. |
| `pero agents ls` | List the Agents, including provider, model, effort, working directory (and whether it is the workspace, the default), permissions, enabled state, the topics each claims, and its note. The main Agent is marked, and so is an Agent whose note has errors while its last good version is in use. `pero agents` alone does the same. |
| `pero agents show <name>` | Show an Agent's settings and the Channels that go to it now (or would, were it enabled), with what each Channel's next turn does: resume its Session, or start a fresh one because the provider or effective folder changed (and whether it starts with the Channel's recent messages). It also shows its note, its topics, which values come from `Pero.md` or Pero's defaults, and its note's errors; a note that has errors and never loaded is named. Warns when its folder is missing or not accessible. |
| `pero channels ls` | List Channels by ID with their address (for Telegram, `<chat_id>` or `<chat_id>:<topic_id>`), topic or chat title, and the Agent that answers there now: the main Agent for a General topic, a group without topics, or a direct chat, and for a topic the Agent whose note's `topic` is its title; `(disabled)` when that Agent is, and `none` when no Agent answers. `pero channels` alone does the same. Channels are created by onboarding, not by hand. |
| `pero channels show <channel>` | Show a Channel by its ID: the Agent that answers there now, what its next turn does with its Session, and how much history it holds. When no Agent answers, it says why: a topic claimed by two notes, a disabled Agent, a note that has errors and never loaded, a topic no note claims, a topic whose title Pero hasn't seen yet, or no note for the main Agent. |
| `pero channels history <channel>` | Print the Channel's latest messages (`-n <count>`, default 20, at most 500) in local time, with direction (`in` or `out`) and origin (`user`, the Agent, `pero` for Pero's own notices, or `workflow` and its name for a delivered Notification). |
| `pero telegram chats` | List allowed chats (kind, title, whether topics are on, whether the bot is an administrator) and chats that recently asked to pair, with their IDs. |
| `pero telegram allow <chat-id>` | Allow a group or direct chat, adding it to `telegram.allowed-chats` in `config.yaml`. A group's ID is negative (`-100…`); a direct chat's ID is the owner's user ID. Both appear in the pairing hint the bot sends to a chat it does not serve yet. |
| `pero telegram deny <chat-id>` | Remove a chat from the allowlist in `config.yaml`. Its Channels and Agents stay and resume if it is allowed again. |
| `pero telegram token` | Set the Telegram bot token from @BotFather. On a terminal it prompts, showing `*` for each character typed, and it reads stdin otherwise, and refuses the token as an argument, so it never lands in shell history. While Pero runs it goes through the daemon, which writes `.env` and switches to the new token without a restart; while Pero is stopped it writes `.env` itself, and Pero uses the token from its next start. Either way `.env` is owner-only and is added to the workspace's `.gitignore`. To remove the token, delete its line from `.env`. |
| `pero workflows ls` | List the Workflows by name with their Agent, schedule (cron and time zone, or `by hand`), next run, the Channels they post to, enabled state, and note; a Workflow whose note has errors while its last good version is in use is marked. `pero workflows` alone does the same. |
| `pero workflows show <name>` | Show a Workflow: its note, Agent, input, schedule with its next and last run, attempts, the Channel history it reads, state, and the Channels it posts to, which its note's `channel` names by topic title, `<chat title>/<topic title>`, `General`, or Channel ID. Lists its note's errors, and warns when its Agent is disabled. A Workflow whose note has errors and never loaded is named with its note. |
| `pero workflows run <name>` | Run a Workflow now, with a schedule or without, and even while it is disabled, which only stops its schedule; its Agent must be enabled. The run waits for a free slot (`max-concurrent-runs`) and for the Workflow's previous run to finish, then prints the Agent's answer, or that it was skipped because its history window had no messages; a failed run exits with status 1 and prints why. `--no-wait` prints the run's ID and returns. A run starts a provider conversation of its own, never a Channel's Session, and adds nothing to Channel history; nobody is there to approve tools, so an Agent with `ask` permissions is refused any tool that would need approval, including a Claude Agent's edits of the settings folder. |
| `pero runs ls` | List the latest Workflow Runs, newest first (`-n <count>`, default 20, at most 500), with Workflow, status, attempt, what started them (`manual`, `schedule`, or `retry of run <id>`), and when they were created and finished. `--workflow <name>` and `--status <status>` narrow it. `pero runs` alone does the same. |
| `pero runs show <run>` | Show a run: status, attempt, what started it, its times, the run that retries it, the Channel history it read (how many messages, from which Channels, and how many the budget left out), the Agent's answer or why it failed, and each Notification it left with its delivery status, attempts, and last error. A failed, interrupted, or cancelled run that is not retried yet says how to retry it. |
| `pero runs retry <run>` | Queue a failed, interrupted, or cancelled run again as a new run keyed `retry:<run>` with the next attempt, then print the Agent's answer as `pero workflows run` does (`--no-wait` returns at once). The owner decides, so the Workflow's `max-attempts` does not limit it, nor does its being disabled, but its Agent must be enabled. The retry reads the same Channel history window and is claimed before the Workflow's other waiting runs; when a run completed since has read some of those messages too, the command notes it. A run has one retry: retrying it again names that retry instead, and a run that completed or has not finished is refused. |
| `pero runs cancel <run>` | Cancel a Workflow Run by ID: one waiting to start is `cancelled` at once and never starts; a running one has its Agent's turn aborted, and the command returns once it is recorded `cancelled`. A run that has finished cannot be cancelled. |
| `pero notifications ls` | List the latest Notifications, newest first (`-n <count>`, default 20, at most 500), with their run, Workflow, Channel, status (`pending`, `delivered`, or `failed`), attempts out of ten, next attempt, and last error. `--status`, `--workflow <name>`, `--channel <id>`, and `--run <id>` narrow it. `pero notifications` alone does the same. |
| `pero notifications show <notification>` | Show a Notification: its Channel, status, attempts, next attempt, last error, delivered message ID, and the message itself, then what stands in the way of delivery: a chat that is no longer allowed, or Telegram not being ready as `pero status` reports it. |
| `pero notifications retry <notification>` | Make a waiting Notification due now, or give a failed one ten fresh attempts starting now, then wait up to 30 seconds for the attempt and say whether it was delivered; a failed attempt exits with status 1 and says why and when Pero tries again. `--no-wait` returns at once. A delivered Notification is refused, since it would be sent twice. It creates no Workflow Run. |

Every command except `init`, `check`, `run`, `run --foreground`, `stop`, `status`, `service`, `logs`, `restore`, `telegram allow`/`deny` (which edit `config.yaml` themselves when Pero is stopped), and `telegram token` (which writes `.env` itself) requires the running daemon. When it is stopped, the command exits with `Pero isn't running — start it with pero run` and does not start it implicitly.

Each command that reads Agents, Channels, Workflows, or runs sends a request to the daemon. Agents, Workflows and their schedules, the installation settings, and which Agent answers in each topic are notes, so their commands only show them; edit the notes to change them. When a topic moves to another Agent, that Agent's first turn there closes the old Agent's Session and starts a fresh one that carries over the Channel's recent messages. A change of an Agent's provider or effective folder makes its next turn in each Channel start a fresh Session; model, effort, and instructions apply from the next turn of the same Session (see the [Session policy](./ARCHITECTURE.md#5-runtime-contract)).

## First run and local files

Pero works on a workspace: `--workspace`/`-w`, then `PERO_WORKSPACE`, then the nearest folder holding `.pero/` from the current folder upward (the home folder itself never counts), then `~/workspace` when it holds `.pero/`. Its state lives in the workspace's `.pero/`. An explicit option or variable always wins over a workspace found from the current folder; with none found, commands say which `pero init` to run. On a first `pero run`, the daemon initializes the SQLite database, applies migrations, and reports ready without Telegram or provider setup. An interactive `pero run` then guides the owner through provider sign-in checks and Telegram setup (the bot token, then pairing a chat, described below) over the control endpoint, explaining the external Claude Code and Codex CLI sign-in commands when needed. A non-interactive run leaves the daemon running in a degraded state and prints the missing settings, each with the command that fixes it, rather than waiting for input. Every answer goes to the daemon at once, so an interrupted setup keeps what was done, and a later `pero run` asks only for what is still missing and checks sign-in again. A provider can be reported unavailable without silently changing billing mode or switching an Agent to another provider.

Only providers in use count toward health: the default provider and any provider an enabled Agent uses. The other one is still listed in `pero status`, marked `(not in use)`, and setup does not ask to sign in to it. The daemon runs `claude auth status` and `codex login status` as its own account when it starts and whenever `pero run` asks.

The Telegram bot token is stored in the workspace's `.env` as `PERO_TELEGRAM_BOT_TOKEN` (owner-only, replaced atomically, and `.env` is added to the workspace's `.gitignore`), never in SQLite, logs, `pero status`, or `pero settings`. A token in the daemon's environment as `PERO_TELEGRAM_BOT_TOKEN` wins over the stored one, which suits a service manager; `pero run` passes its own environment to the daemon it starts. Changing the token takes effect without a restart.

### Telegram setup

The recommended path gives each Agent its own topic in one private group:

1. Create a bot with [@BotFather](https://t.me/BotFather) and give Pero its token (`pero run` asks for it).
2. Create a private group, turn on **Topics** in its settings, and add the bot as an administrator. No specific administrator right is needed; without administrator rights Telegram shows the bot only commands, mentions, and replies. Anyone who can write in an allowed group can talk to its Agents, so Pero reports a public group as a danger.
3. Allow the group. An interactive `pero run` first asks where the owner will talk to Pero, a private group (recommended) or a direct chat with the bot, and shows the steps for that one. It waits for the bot to be added or messaged, offers to allow that chat (the bot tells the chat to confirm it in the terminal), then waits for the bot to be made an administrator and for a public group to be made private; otherwise the bot answers the group with its chat ID, and `pero telegram allow <chat-id>` allows it. Allowing a chat that asked to pair posts the first steps in it at once. Turn on topics before allowing the group: that change gives the group a new chat ID. Pero follows the change if it happens later.
4. Create a topic per Agent. Pero writes the topic's Agent note, such as `Agents/Groceries.md`, from `Agents/_Template.md` when you've added one, with `topic` set to the topic's title, and posts a welcome there naming it; editing that note, or asking the Agent to, changes its instructions, provider, or folder. Every topic's Agent starts with the main Agent's instructions. The General topic talks to the main Agent (`Main.md` unless `main-agent` names another).

A direct chat with the bot works as well, alone or next to the group: message the bot and allow the user ID it replies with. It has no topics and talks to the main Agent, in a Session of its own.

```text
~/workspace/
├── .env                 # the Telegram bot token; owner-only, Git-ignored
├── .pero/
│   ├── config.yaml      # the data folder and the allowed chats
│   ├── pero.sqlite      # runtime state and message history
│   ├── logs/
│   │   ├── pero.log     # daemon logs, JSON lines
│   │   └── daemon.out   # raw stdout/stderr of a daemon started by `pero run`
│   └── run/             # local control endpoint and process metadata
└── data/
    └── Settings/        # Pero.md, Agents/, and Workflows/
```

Provider subscription credentials remain in the provider CLIs' own stores under the same OS account. The Telegram bot token is a separate secret, in `.env` or the service environment. Never place provider credentials or Telegram tokens in notes, database rows, or diagnostic output.

## Process and command boundaries

The npm executable is a thin command entry point: `bin/pero.js` loads the compiled [nest-commander](https://nest-commander.jhunt.dev/) CLI, which runs `CommandFactory.run(CliModule)`. `CliModule` imports only what commands need, not the full daemon `AppModule`, so commands start quickly without booting Telegram, the scheduler, or provider SDKs. `pero run` launches the NestJS daemon as a separate background process with logs redirected to local files, then waits for a readiness response. Node's [detached subprocess documentation](https://nodejs.org/docs/latest-v24.x/api/child_process.html#optionsdetached) describes the required detached/unreferenced process and disconnected standard I/O behavior. The daemon owns Telegram intake, scheduling, execution, notification delivery, and exclusive access to SQLite. A private local control endpoint serves lifecycle and management requests from the CLI; it must be accessible only to the owner account. The CLI never opens the database or loads TypeORM: it is a client of the control endpoint, sharing request schemas with the daemon. This keeps a single writer and ensures only the daemon runs migrations. Commands that need no database, such as `init`, `check` without Pero, and `telegram allow`/`deny` while Pero is stopped, read and write the workspace's files themselves.

Once the database is open and migrated, the daemon must start and report ready even when settings are missing or invalid. A bad Telegram token, a signed-out provider CLI, or an invalid Agent folder marks that component degraded in `pero status` instead of failing startup, so the owner can always fix configuration with ordinary commands. Only file-level maintenance that requires a stopped daemon, such as restoring a backup, runs without it.

Permit only one daemon per workspace. Use an exclusive runtime lock and verify a live control endpoint before treating stored process metadata as current; a PID alone can be stale or reused. `pero stop` uses the control endpoint for graceful shutdown instead of killing whatever happens to have a saved PID. Database migrations happen before the daemon reports ready. `pero run` reports startup failures, printing the daemon's own output from `logs/daemon.out` and where to find the logs.

`pero run` keeps the process alive after the invoking terminal exits. Automatic startup after login or reboot is a separate service-manager feature, not implied by this command: `pero service install` sets it up with systemd or launchd, and the foreground mode provides a stable entry point for them or another supervisor. Pero exits cleanly on `pero stop`, so a service restarts it only after a crash. Upgrading the global npm package does not replace a running process; restart Pero to use the new version, with migrations run on startup.

## Packaging checks

The package must include the built CLI and daemon files, migrations, and runtime dependencies. Test installation from the packed npm artifact on supported operating systems and architectures, not only from a source checkout. [`better-sqlite3`](https://github.com/WiseLibs/better-sqlite3#installation) supplies prebuilt binaries for major platforms, but unsupported combinations may need a local build toolchain; make this a release check. Confirm that global installation creates a working `pero` command, first-run setup works under an ordinary user account, and `run`/`stop`/`status` work after a terminal closes. CI runs `scripts/check-packed-install.sh` on every supported OS and Node version: it installs the `npm pack` artifact into a temporary global prefix, loads `better-sqlite3` from it, and runs `run`, `status`, `backup`, `stop`, and `restore` from a fresh home directory.
